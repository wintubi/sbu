# 项目需求基线 v0.2

状态：已表达目标与建议方案分开记录；未完成产品及技术定稿。

## 一、已经明确的共同要求

- 两个项目都是纯软件的大模型应用，需要可运行的代码、可视化演示和可解释的技术方案。
- 开发过程也是用户学习如何开发软件的过程，需留下调研、讨论、决策、评审、测试和复盘。
- 小范围验证先行；验证后细化总体规划，再按模块讨论、明确与实现。
- 采用规格驱动协作，需求和设计明确后才开发；已批准范围内的常规实现持续推进。
- 项目代码最终集中到当前仓库各自的项目目录；交接文档应能由其他 AI 独立阅读。
- 面试材料随真实进展更新，区分用户贡献、参考复用、计划与已验证结果。

## 二、旅行项目要做什么

**最终业务目标（来自用户描述）：** 面向本地生活，把灵感发现、地点识别与核验、地图及路线查询、单日/多日行程优化和活动信息获取串联起来，输出带地点依据的可执行方案与信息清单。

用户提出的具体场景包括“行程判官”和活动/热点查询。购票信息及跳转可以是后续能力；实际支付、订单、核销、平台合作及自动触达目前没有确认实施范围，不能当作既有闭环。

**可参考的已有工作：**

| 基础 | 能参考什么 | 不能据此认定什么 |
|---|---|---|
| 第 13 章 HelloAgents 代码 | Vue/FastAPI、四角色固定编排、MCP 配置、结构化结果与展示 | 用户独立从零实现、动态调度、大小模型协同或真实业务端到端通过 |
| 上传的出行 DOCX | 单 ReAct Agent、多工具配置、异步 API、会话与生命周期示例 | 多 Agent、持久恢复、完整行程优化、订单交易已完成 |
| 用户提供的简历和经历 | 业务背景、竞品调研线索、目标与历史探索 | 暂缺报告的市场结论与性能数字已复核 |

**建议首轮验证：** 用户输入同一城市的一天、3–6 个已有候选地点及时间/交通条件，系统完成地点核验、时间与路线检查、有限调整，并明确解释冲突和未知信息。
先验证“方案可信吗、能执行吗”，再扩展灵感获取和多平台活动搜索。该范围仍待用户确认。

**建议阶段方向：**

1. 单日行程核验小闭环及真实工具契约。
2. 多日拆分、偏好与预算、行程修改与局部重算。
3. 灵感输入、活动清单、时效与来源核验。
4. 允许范围内的购票信息/跳转；若要订单或主动推荐，另立规格与评测。

## 三、年画项目要做什么

**最终业务目标（来自用户描述）：** 面向木版年画数字化保护、展示与研究探索，从扫描 PDF、作品图和说明中提取作品及局部人物、器物等知识，以 CIDOC CRM 为参考构建领域本体；迭代本体并批量处理，形成带证据的知识图谱，支持跨作品关系探索和检索增强问答。

**可参考的已有工作：**

| 基础 | 能参考什么 | 限制 |
|---|---|---|
| 上传的成果 README | OCR、三层本体、词表、图文抽取、质量控制、Neo4j、展示和评估的旧路线 | 未取得完整源码、数据、标注与运行结果 |
| 用户的领域解释 | 以作品为中心，图像局部独立组织，知识带来源，本体多版本迭代 | 具体类、关系和规范需要实际样本验证 |
| kgConstruct 链接 | 旧版本线索 | 当前读取失败，不能声称已审查代码 |
| 已讨论的 Harness 思路 | 任务状态、证据、有限修复、人工审核和本体版本管理 | 这是改进方向，不是已经实现的平台 |

**建议首轮验证：** 小批真实作品资料，从页面和图像配对到带证据的结构化抽取，完成校验、最多有限次修复、未决项展示、人工复核及小型图谱发布。
本体只冻结一个最小版本，AI 生成的本体变更保留为建议；不让生产批次自行改正式本体。

**建议阶段方向：**

1. 小批证据化抽取与人工复核闭环。
2. 批处理恢复、质量诊断和固定流程/Agent 对照实验。
3. 本体变更提案、版本回归与影响分析。
4. 跨作品文本/图谱/图像检索及有证据的问答与展示。

## 四、两个项目的区别

| 维度 | 旅行 | 年画 |
|---|---|---|
| 主要时效 | 查询当时的地点、交通、活动与天气 | 来源版本、编目语义和历史材料 |
| 主要用户动作 | 提交条件、检查行程、修改安排 | 导入资料、核对证据、裁决疑难项、发布知识 |
| 核心失败 | 地点错、时间冲突、工具失败伪装成功 | 作品配错、无证据推断、实体误合并、来源丢失 |
| 推理价值 | 处理偏好和冲突、选择调整方案 | 在不确定项上选择补证与修复策略 |
| 确定性代码职责 | 时间计算、路线矩阵、格式与约束校验 | 来源定位、Schema/关系校验、版本与发布一致性 |
| 质量证明 | 可行性、事实核验、延迟和成本 | 正确性、证据支持、覆盖与人工审核负担 |

两个应用可复用少量模型调用、日志和评测习惯，首版不先抽象成共用平台，不用技术栈名称区分项目价值。

## 五、现在需要什么产物

需要的是可审阅、可接手的需求和规格草案：问题/用户/范围、数据样例、处理流程、接口与状态、技术推荐及代价、异常与恢复、测试验收和任务依赖。
现阶段不需要一次性生成两个完整代码库，也不把未讨论的架构和效果数字写成既定事实。

**确认范围之后的正式产物：** proposal、design、行为 specs、tasks、决策记录、设计评审；实现后补代码评审、verify、交接与复盘。若使用 sdflow，按其当时有效的工具链和版本执行。
