## 1. 推荐定位

建议名称：**多 Agent 本地生活行程规划与核验助手**。

核心问题是“用户要在灵感、地点、交通和活动信息之间反复查询，才能判断一个安排能否执行”。
首个产品切口建议是“行程判官”：核验和优化用户已有行程。灵感自动获取、活动订阅、购票跳转为后续独立模块，交易支付和核销不属于当前已实现范围。

## 2. 现有源码链路

```text
Vue 表单：城市 / 日期 / 天数 / 交通 / 住宿 / 偏好 / 额外要求
  → POST /api/trip/plan
  → MultiAgentTripPlanner
```

## 5. 面试追问与答题要点

### 为什么用多 Agent？

现有原型用角色区分提示词和工具职责，方便观察各阶段输出。但天气查询通常可以是确定性工具调用，不必为每次查询额外安排一个模型角色。多 Agent 的收益需要对照“单 Agent + 工具”和固定工作流验证，不能用角色数量证明先进性。

### 这是动态多 Agent 调度吗？

当前是四角色固定顺序协作，角色之间通过编排器传递文本；没有证明动态任务分解、并行调度、共享黑板或协商决策。后续只有在实际任务需要时才增加相应机制。

### LangChain、LangGraph 和 HelloAgents 各自做什么？

当前代码使用 HelloAgents。LangChain 是另一套应用组件生态；LangGraph 可用于状态化流程和中断恢复。面试讲实际版本，不能因机制类似就替换框架名。是否迁移需要比较改动成本与新增需求。

### MCP 带来什么？为什么不直接调 API？

MCP 提供标准化工具接入方式，可复用工具描述与调用接口。但它并不自动完成高德结果到领域模型的转换，也不保证时效、正确性和权限。只有一个稳定供应商时，直接 HTTP API 也可能更简单，需比较维护与调试成本。

### 接了 MCP 为什么不能叫热插拔？

现有实现固定启动 `uvx amap-mcp-server`。运行中添加、更换和移除工具，还需要生命周期、配置刷新、兼容性与在途请求处理；目前未验证这些能力。

### 你做了大小模型协同吗？

当前可见版本四个角色共享单个模型，不能据此回答已经做了。后续可以实验按任务复杂度路由，但要先明确候选模型、升级条件、成本和质量约束，并记录错误路由率。“换不同模型试过”也不等于协同推理架构。

### 行程怎样保证真实和可执行？

目前的提示词和 Pydantic 主要解决格式问题，不能保证事实。建议把真实 POI ID、来源时间、坐标和营业/活动时间作为证据，配合路线耗时和停留时间检查。未知信息明确标记，无法核验时不生成确定性承诺。

### 目前最重要的工程问题是什么？

失败兜底会生成占位景点和坐标，接口仍可能返回成功；地图独立 API 也会把未解析结果表现为空列表。优先建立成功、部分完成、失败和演示数据的区别，再补结果解析和错误传播。这是当前审查结论，不是已完成修复。

### 为什么叫路线优化？

当前只能说“行程生成”：规划提示词要求考虑距离，但实际主链路没有显式路线调用和约束求解。后续首版建议在真实时间矩阵、开放时段和停留时长上做可行性检查及简单重排；如果只是启发式方案，不声称全局最优。

### 交易转化和“服务找人”体现在哪里？

它们目前是业务设想。用户填写表单后得到行程，属于主动请求服务。主动推荐需要订阅偏好和触达机制；交易需要库存、订单、支付/跳转及回传记录。提供链接最多说明导流，不能算成交。

### 怎么做评测？

以下为待确认方案，不是已完成实验：先用固定 POI、路线与天气响应回放做可重复评测，再单独做真实服务联调。覆盖同名地点、闭馆、跨城、时间冲突、恶劣天气、工具超时和修改条件等用例。固定输入、工具快照和预算，对照单 Agent、现有多角色流程和加校验版本。

### 有哪些效果数据？

本次没有可核验的线上用户、转化、延迟分位数或规划成功率。已有验证只覆盖前端安装、模块 HTTP 响应和 Vite 打包，标准 TypeScript 构建仍有错误。不能拿页面打开或 JSON 解析成功代表有效规划成功率。

## 6. 未来指标定义草案

- **有效任务完成率**：满足预先定义硬约束、关键地点已核验且无伪造兜底的任务数 / 全部约定任务数；超时和失败计入分母。
- **硬约束违规率**：违规约束数 / 可判定的适用约束数，同时报告“存在任一违规的行程比例”；未知约束另报。
- **POI 匹配准确率**：与人工确认地点相符的匹配数 / 有标注的匹配数；歧义和未匹配另报，避免只看已匹配项。
- **修复有效率**：在预算内修复且未引入新硬约束违规的任务数 / 进入修复的任务数。
- **延迟与成本**：整体任务 p50/p95、模型调用数、工具调用数、每任务成本；成功与失败分别统计。

同一任务可能存在多个合理行程，不用唯一参考文本匹配衡量整体质量。主观偏好满意度与硬约束质量分开。

## 7. 最小验证候选

推荐输入：一个城市、一个出游日、少量已选地点、出发位置、出行方式和时间范围。
推荐输出：已核验地点、路线耗时、时间冲突及调整建议、来源与未知项。
先验证工具结果可用、失败不伪装成功和行程约束检查，再讨论大小模型和更复杂调度。具体样本、阈值和技术方案评审确认后才实现。
