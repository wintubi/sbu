# 本地生活旅行助手：首版规格草案 v0.2

日期：2026-11-06（Asia/Shanghai）。状态：DRAFT / 未批准实现。
本文件可供下一位 AI 接手讨论；首版范围、技术推荐、预算和测试样本均需评审确认。不是已经通过 sdflow/OpenSpec 校验的正式 change。

## 1. 产品目标与首版建议

最终目标是把灵感、真实地点、路线、活动信息和行程调整串起来，帮助用户形成可执行的本地生活出游方案。

**建议首版：单日“行程判官”。** 用户已有 3–6 个候选地点，系统识别地点、获取必要事实、检查时空约束，给出可行安排或明确的冲突/未决项。它验证可信度与可执行性，之后再增加灵感发现、多日规划与活动清单。

首版以同一城市、一天、一个出行方式、一个可信本地用户为实验范围。没有下单、支付、核销、订阅触达或平台爬取的开发承诺。范围是本轮推荐，未取消远期目标。

## 2. 用户与关键场景

- **U1 已有地点清单**：用户输入地点、出发位置和当天时间，得到地点核验、顺序与预计到离时间。
- **U2 行程冲突**：闭馆、预约时段或路程导致不可能完成时，指出冲突依据并提出调整；不通过虚构时间使行程成立。
- **U3 地点歧义**：同名地点无法确定时，展示候选让用户选择，不静默选一个地点。
- **U4 条件修改**：用户删除地点或改变时间后创建新版本，保留旧结果，重算受影响安排。
- **U5 工具不可用**：明确展示缺失、过期或失败状态，给出部分结果或失败原因。

## 3. 已有基础和缺口

参考源码在 `HelloAgent学习记录/code/chapter13/helloagents-trip-planner/`。可读到 Vue、FastAPI、Pydantic、HelloAgents 四角色固定流程、MCP 高德配置及结果展示。
目前地图独立 API 的多项结果解析未完成，规划失败会生成占位景点，接口可能仍标成功；主规划链没有显式路线调用或营业时间约束检查。
此前只验证前端安装、模块响应及单独 Vite 打包，标准 TypeScript 构建失败。后端真实联调未验证。

DOCX 可参考单 ReAct Agent、多工具配置、异步调用与资源生命周期，但不证明本项目多 Agent 或业务闭环。历史个人贡献、竞品报告、大小模型方案仍待补证。

## 4. 功能要求与验收场景

以下“应”均为草案候选，待批准后成为该版本验收要求。

### T-01 输入与时间一致性

系统应校验城市、日期、时区、出发位置、地点清单、交通方式、停留时长和时间范围。

- WHEN 日期非法、出发晚于结束、停留时长非正、跨城或地点数超出首版范围；THEN 返回明确的字段/范围错误，不调用模型和地图。
- WHEN 缺少影响可行性的必要信息；THEN 请求补充或标为待确认，不能默认伪造。

### T-02 地点核验

每个确认地点应关联供应商 POI ID、名称、坐标、查询来源与时间。

- WHEN 出现两个合理同名候选；THEN 结果进入 needs_input 并列出候选，用户选择后新建后续运行。
- WHEN 没有匹配；THEN 明确未匹配，不能使用模型生成坐标补齐。

### T-03 工具结果规范化

工具适配层应区分有效、空结果、超时、供应商错误、格式错误与不支持能力。

- WHEN MCP 调用成功但响应无法解析；THEN 记录解析错误，不返回“查询成功 + 空列表”。
- WHEN 天气日期超出供应商覆盖范围；THEN 标为 unavailable，不把当前天气当目标日预报。
- WHEN 供应商不提供营业/预约信息；THEN 保留 unknown；人工补充的信息标明输入来源。

### T-04 行程可行性与调整

系统应使用可获取的路线时间、停留时长、出发/结束时间和已知开放/预约时段检查约束。

- WHEN 路程与停留时间已超过时间窗口；THEN 输出不可行原因和可选调整，保留未满足约束。
- WHEN 调整顺序或减少地点；THEN 说明变化及依据，并重新执行约束检查。
- WHEN 关键约束未知；THEN 结果标为部分核验，不能宣布已证实可行。

首版可采用简单启发式重排，不要求全局最优；优化目标和硬约束必须可检查，不能以提示词要求“考虑距离”替代实现。

### T-05 执行状态、预算与恢复

每次运行应持久化 request、阶段、规范化工具结果、版本和预算消耗。保存动作与简短决策理由，不要求输出模型隐藏推理。

- WHEN 模型/工具超过次数或总时限；THEN 停止继续调用，保留已获得结果，标记预算耗尽。
- WHEN 在已保存阶段后重启；THEN 从最近可恢复状态继续，不伪称所有远程调用都只执行一次。
- WHEN 同一幂等键和相同请求重复提交；THEN 返回同一运行；相同键配不同请求返回冲突。

### T-06 结果与界面

界面应展示输入、地点匹配、时间线、路线/时间依据、问题清单和调整说明；地图为有条件的增强显示，缺少前端地图凭据时保留可用列表与时间线。

- WHEN 返回部分结果、needs_input 或 failed；THEN 明显区分，不能用占位景点构造有效方案。
- WHEN 完成演示回放；THEN 页面标明 replay，不能伪装为实时查询。

## 5. 数据契约草案

所有 ID 由系统生成；时间使用带偏移的 RFC3339，另存 IANA 时区。首版示例默认 Asia/Shanghai，仍需显式记录。距离单位米，时长单位秒，经纬度需要合法范围。

| 对象 | 最小字段 |
|---|---|
| TravelRequest | city, date, timezone, origin, time_window, transport, candidates[{name或poi_id, stay_seconds, optional_time_window}], preferences |
| Run | run_id, request_id, parent_run_id?, request_hash, status, current_stage, versions, budget, created_at, updated_at |
| POIRecord | internal_id, provider, provider_poi_id, name, city, coordinates, fetched_at, evidence_refs, match_status |
| Fact | fact_id, subject_id, field, value或unknown, source_type, source_ref, fetched_at, valid_for?, provider_status |
| RouteLeg | from_poi_id, to_poi_id, transport, duration_seconds, distance_meters, source_ref, fetched_at |
| ItineraryResult | run_id, revision, quality_status, visits[{poi_id,arrival,departure}], legs, issues, changes, evidence_refs |

`run.status`：queued / running / needs_input / completed / failed / cancelled。
`quality_status`：verified_feasible / infeasible / partially_verified / unverified。
completed 仅表示处理结束，不代表行程可行；missing fact 不以 0、空字符串或猜测事实代替。

候选事实的有效范围、缓存时间和允许过期程度根据供应商与字段确定，写入配置和报告；不对所有数据使用一个未经讨论的统一 TTL。

## 6. API 草案

| 接口 | 行为 |
|---|---|
| POST /api/v1/travel/runs | 校验请求，接受后返回 202 与 run_id；幂等键见 T-05 |
| GET /api/v1/travel/runs/{run_id} | 返回阶段、状态、问题及已有结果，不暴露凭据 |
| POST /api/v1/travel/runs/{run_id}/revisions | 明确提交候选选择/条件变化，创建带 parent_run_id 的新运行 |
| POST /api/v1/travel/runs/{run_id}/cancel | 尽力停止后续调用，报告已有调用状态，不声称撤销远端已执行操作 |
| GET /health/live | 进程存活，不执行收费模型请求 |
| GET /health/ready | 报告数据库、worker 和所选运行模式的必需能力；replay/live 分开 |

错误响应统一为 code、message、retryable、run_id?、field_errors?。HTTP 业务错误、任务状态和质量状态分层表达。具体异步轮询频率在接口设计时确定，不依赖 WebSocket 才能演示。

## 7. 推荐架构与技术栈（待调研验证）

```text
Vue 界面 → FastAPI → 任务/状态存储
                      ↓
输入标准化 → 地点解析 → 事实/路线获取 → 候选安排 → 确定性校验
                                          ↑              ↓
                                        有限调整 ← 诊断 / 结束
```

| 层 | 首版推荐 | 依据与代价 |
|---|---|---|
| 界面 | Vue 3 + TypeScript + Vite | 可参考已有页面；先修类型错误，不能跳过标准构建作为验收 |
| API/契约 | Python 3.12、FastAPI、Pydantic | 已有基础；Schema 合法不等于业务事实正确 |
| 编排 | 优先验证 LangGraph 状态图；HelloAgents 方案作备选 | 贴合状态/中断需求，但会增加迁移与版本学习成本；先做最小兼容验证再定 |
| 模型 | 一个可配置的支持结构化输出/工具调用的服务 | 先建立基线，大小模型路由为后续实验，不先堆模型 |
| 地图 | 领域适配器下接高德 MCP，保留直连 HTTP 候选 | 保持数据契约，比较解析、稳定性、配额与维护成本 |
| 存储/执行 | 单进程本地 SQLite + 持久任务状态与 worker | 首版运行简单；不承诺多实例，checkpoint 与业务状态需定义清楚避免双真相源 |
| 测试 | pytest、工具录制回放、前端构建、一个 UI E2E 路径 | 不以 mock 通过代替真实接入验证 |

不先引入向量数据库、消息队列、Kubernetes 或大小模型推理平台。若真实需求使其必要，单独记录依据与变更。
具体依赖版本在兼容实验后锁定；参考 DOCX 的旧 API 不作为锁版本依据。

## 8. 边界与预算草案

运行模式为 replay 或 live，分别配置和报告。模型、供应商与工具响应版本可追溯。
候选预算：每次任务最多 10 次外部工具调用、2 次调整轮次、90 秒总体时限；模型调用与 token/费用另设配置上限。数值是待评审起点，未实测，不能作为性能承诺。
工具失败可做有限重试，所有尝试计入预算；取消/重启后记录不确定的在途调用。
同步供应商 SDK 不得直接阻塞 async 请求链；具体采用异步 SDK 或线程/worker 隔离并测试。

首版只作为可信用户的本地演示。若要公网多用户服务，需另补用户认证、数据归属校验、限流、部署配置和授权测试；客户端 thread_id 本身不是授权。

## 9. 测试与验收计划

建议先准备 20 个可回放任务：6 个可行、4 个时间冲突、3 个地点歧义、2 个天气覆盖不足、3 个工具失败/格式错误、2 个条件修改。数量与分组在规格确认时冻结，不把这些写成已有数据。

| 层 | 必须验证 |
|---|---|
| 单元/性质 | 时间计算、单位转换、窗口检查、排序后约束、非法输入 |
| 契约 | MCP/HTTP 原始返回到 POI/Fact/RouteLeg；空、错、超时分别传播 |
| 集成 | SQLite 与任务恢复、幂等、取消、条件修改、预算停止 |
| E2E | 输入→进度→结果；歧义选择→新运行；工具失败明确展示 |
| 真实服务 | 有凭据后至少记录 POI、路线、天气三类必要请求的真实结果及限制 |
| 模型对照 | 固定工具快照下比较固定流程/单 Agent 与候选方案，报告质量、延迟和实际成本 |

**首版软件门槛候选：** 标注为必需的确定性回归全部通过；无占位结果伪成功；需要输入和未核验状态正确展示；重启恢复和幂等用例通过；标准构建通过。
**效果门槛待定：** POI 匹配、行程有效完成率、p95 延迟和成本目标必须在真实样本与预算讨论后补齐。阈值未定或真实接入未测，不宣称业务效果验收完成。

回放测试结果和在线验证分开；20 个任务只能支持小规模验证，不能推断总体用户满意度或商业转化。

## 10. 实施工序建议

| 顺序 | 任务 | 依赖 | 可检查产物 |
|---|---|---|---|
| 0 | 收敛首版范围、样例、预算与验收 | 用户讨论 | 正式规格与设计评审结论 |
| 1 | 版本兼容实验，冻结领域模型与工具契约 | 0 | 锁文件、最小请求、replay fixture |
| 2 | 端到端切片：有效数据返回及失败不伪成功 | 1 | 一个可运行 API 和简单结果页 |
| 3 | 时间/路线校验、有限调整与来源展示 | 2 | 冲突与可行案例 |
| 4 | 持久状态、幂等、恢复、取消与修改 | 2；与 3 的状态接口先确定 | 恢复/修改/重复提交测试 |
| 5 | 固定集回放、真实工具联调、展示验收 | 3、4 | 实际报告与已知限制 |

不按“先写完所有后端再写界面”拆工序。每个小任务都贯穿可观察的数据链路。

## 11. 后续路线与面试交付

首版验证后，按需求基线细化多日优化、灵感/活动模块和导流能力，每个模块有自己的规格与验收。并发容量和部署形态根据目标使用场景确定。

交付面试材料包含：实际框架与模型版本、两个数据通路、为什么选工作流/Agent、真实失败案例、约束检查方法、对照结果与个人贡献。没有测量就不写提升百分比，不把跳转链接称为交易完成。

## 12. 进入实现前的待决项

P1 用户是否接受“已有地点单日核验”作为首版？
P2 模型和地图渠道的实际可用性、预算与运行方式？
P3 开放/预约信息拿不到时，用户补充还是保留部分核验？推荐两者都允许并标来源。
P4 样本、验收阈值和代码复用范围；编排框架在最小实验后定。
以上未被用户确认，本文件不授权下一位 AI 直接实现完整系统。
