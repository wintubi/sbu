## 结论

旅行项目突出在线工具使用、行程约束和服务体验；年画项目突出多模态知识质量、证据追溯和评测方法。二者都可以建设 Agent Harness，但业务目标和验收标准不同，不应仅靠不同提示词包装成两个相同项目。

| 维度 | 本地生活旅行助手 | 木版年画知识抽取与质量评测 |
|---|---|---|
| 用户 | 有明确或模糊出游需求的人 | 编目人员、研究者、文化资料整理人员 |
| 输入 | 地点、时间、偏好、预算、已有行程；灵感输入为待开发扩展 | 扫描图录、作品图、描述、已有本体与词表 |
| 输出 | 有真实地点依据、满足约束的行程及修改说明 | 带来源证据的结构化知识、未决项及质量报告 |
| 主要不确定性 | POI 匹配、营业/活动时间、实时交通和第三方工具可用性 | OCR、图文配对、视觉身份判断、实体归一、来源冲突 |
| 核心技术能力 | 工具集成、约束检查、规划与局部重排、API 服务 | 本体约束、多模态抽取、证据建模、诊断与受控修复 |
| 验收重点 | 硬约束违规、POI 正确性、有效任务完成、延迟和成本 | 字段及关系正确性、证据支持、未决项处理、人工审核工作量 |
| Harness 重点 | 工具失败降级、状态管理、修改后的局部重算 | 批任务恢复、来源与版本、修复预算、审核及回归评测 |
| 展示重点 | “为什么这样安排，改一个条件会怎样” | “这条知识从哪里来，为什么可信，哪里仍未知” |

两个执行通路必须区分：规划 Agent 直接使用共享 MCP 工具；独立地图 API 通过 `AmapService`。后者未完成不证明前者必定失败，前者有调用代码也不证明独立 API 已完成。

### 明确发现的问题

1. `app/services/amap_service.py:86`、`:115`、`:181`、`:212` 仍是结果解析 TODO，分别返回 `[]`、`[]`、`{}`、`None`。
2. `app/agents/trip_planner_agent.py:368`、`:370` 及附近：JSON 解析失败会生成备用计划，其中景点名称和坐标为占位内容；`app/api/routes/trip.py:48` 仍构造 `success=True`。需要将失败、部分完成、演示数据和有效结果分开。
3. `app/api/routes/trip.py:78` 访问 `agent.agent`，当前 `MultiAgentTripPlanner` 定义中不存在该属性，属于静态确认的接口不一致；未进行真实后端请求复现。
4. 同步 `.run()` 和 `plan_trip()` 位于 async 路由中，存在阻塞事件循环的风险；当前没有并发压测，不能报吞吐数字。
5. 当前规划流程没有显式调用路线规划，也没有营业时间、路径耗时与预约时段的确定性约束检查；提示词要求“考虑距离”不能算路线优化算法。

## 年画材料核查结果

README 描述了 PaddleOCR-VL、CIDOC CRM v7.1.3 复用、宏/中/微三层本体、受控词表、图文联合抽取、五层质控、冲突消解、过滤—重排—有限修复、Neo4j 导入、应用原型和消融评测。它是历史成果线索，不能替代对应资产。

需要进一步核对：

- 11 卷是资料规模、处理规模还是验收规模；不能写成全量高质量完成。
- 北京样卷、河北 50 例展示与山东上卷的历史口径差异；按实际文件和评测运行统一。
- 宏观、中观、微观分别包含哪些类和关系，不能仅根据名称推定具体定义；它们是项目分层，不是 CIDOC CRM 的标准三层。
- 字段正确率、证据支持率、任务完成率是否已有标注、分母和脚本。
- 开发/回归/验收隔离、同预算对照、回放与本体升级检查是否真正运行过。
- “Cypher 命中率 92%”的样本、分母、运行时间及含义；查询可执行、有返回和答案正确是三个指标。

## 已查阅的官方资料及用途
